\section{Goal and summary}
Our project asks where each stage of an edge RAG pipeline should run on a machine whose CPU, integrated GPU (iGPU) and NPU share one DRAM. The pipeline is: query $\rightarrow$ \textbf{S1} embedding (bge-small-en-v1.5) $\rightarrow$ vector search $\rightarrow$ \textbf{S2} rerank (bge-reranker-base) $\rightarrow$ \textbf{S3} generation (Qwen2.5-1.5B-Instruct, INT4). Each model is loaded once on one device. Phase 1 only measures: can every stage run on every device, how fast and at what cost, and why do devices differ.

\textbf{Main findings.}
\begin{itemize}\setlength\itemsep{0pt}
\item All 9 stage$\times$device combinations run on the requested device, with no runtime fallback.
\item The iGPU is the fastest device for S2 and S3 at every size we measured. The NPU is competitive only for small encoder inputs (S1 batch 1; S2 with 10 candidates) and degrades sharply for larger shapes. The CPU is 15--20$\times$ slower for S2 and for S3 prefill.
\item End to end, all stages on the iGPU is best for latency, throughput up to $\sim$2.4 queries/s, and answer quality. Moving S2 to the NPU adds 110--140\,ms per query when S3 is on the iGPU or CPU (nothing when S3 is also on the NPU), lowers recall@3 from 0.87 to 0.82--0.83, and gives at most a few percent more capacity.
\item Placing S1 on any device changes end-to-end latency by about 20\,ms or less; S1 is irrelevant to the decision.
\item Running two devices at once slows both, because they share memory bandwidth: S3 decode on the iGPU slows by 58\% while an NPU reranker runs.
\end{itemize}

\section{Setup}
\textbf{Machine.} An Intel Core Ultra 7 356H (16-core CPU, Arc iGPU and NPU, sharing 96\,GB of DRAM) running OpenVINO 2026.4.1 with OpenVINO GenAI. The machine is shared with other users (load average 1--8 during runs).

\textbf{Models.} S1 and S2 are FP16 OpenVINO exports with static shapes (S1 $[b,64]$, S2 $[k,256]$, padded and truncated), because the NPU requires static shapes; the same shapes are used on all devices. S3 is INT4 with symmetric, channel-wise weights; a first asymmetric export produced garbage on the NPU. Decoding is greedy, at most 32 new tokens in the pipeline.

\textbf{Data.} A closed corpus of 25,880 Wikipedia passages (SQuAD train/dev and HotpotQA). Search is exact cosine similarity in numpy on the CPU ($\approx$4\,ms) and is not part of placement. Phase 1 uses the first 100 of 500 SQuAD-dev questions (20 candidates, top-3 passages to S3); 500 HotpotQA questions are held out for Phase 2.

\textbf{Protocol.} Stage sweeps vary one input at a time: S1 batch (1/8/32), S2 candidates (10--100, real candidates), S3 prompt (256/1k/4k) and output length (32/128/256). They report warm medians over 10 repetitions (S3: 5 on the iGPU, 3 on CPU and NPU); S3 uses a fresh prompt per repetition so the prefix cache cannot inflate results. End-to-end runs process 100 questions under a fixed mapping, sequentially or overlapped (S1/S2 of query $i{+}1$ with S3 of query $i$). Load runs use closed-loop clients (1/2/4) or Poisson arrivals (0.5--3 q/s). Contention runs measure S3 decode while S2 loops on another device.

\textbf{Instrumentation} (no root). \emph{Placement}: \texttt{EXECUTION\_DEVICES} for S1/S2; for all stages, the iGPU cycle counter (DRM fdinfo) and NPU busy counter around each call. \emph{Memory}: a 20\,ms sampler of RSS, iGPU GTT and NPU memory; footprint is load peak minus baseline. \emph{Transfer}: S1/S2 calls are split into tokenize, set input, infer and get output, and infer is repeated with zero-copy tensors to estimate the input copy. \emph{Cold start}: NPU driver and iGPU kernel caches disabled.

All nine pairs run with no silent CPU fallback. The NPU is the least flexible device: it needs static shapes, including a maximum prompt length for the LLM, and compile cost grows quickly with shape. The compile cache hides this after the first load (reranker 0.12\,s warm, 68\,s cold); iGPU cold loads cost only 0.5--1.4\,s more.

\textbf{S1.} All devices take under 10\,ms at batch 1, where the iGPU and NPU are close (iGPU 1.4--2.9\,ms depending on the run, NPU 2.4\,ms) and fixed overhead dominates. The iGPU scales best and the CPU worst. \textbf{S2.} The iGPU is the best choice from 10 candidates up. The NPU matches it only at 10 candidates, is 1.6$\times$ slower at 50, and collapses at 100 (14\,s).

\textbf{S3.} Prefill is the large difference (Fig.~\ref{fig:s3}): at 1k tokens TTFT is 146\,ms on the iGPU, 771\,ms on the NPU and 2932\,ms on the CPU. Decode speed is 69--75 tokens/s on the iGPU, 47--58 on the NPU and 40--56 on the CPU; decode is memory-bandwidth bound, so the gap is much smaller than in prefill. On the iGPU, output length does not change TTFT or time per output token (TPOT 13.3--14.6\,ms), so total time is linear in output tokens. The NPU's TTFT depends on the compiled prompt limit rather than the real prompt: a 256-token prompt takes 99.6\,ms with \texttt{MAX\_PROMPT\_LEN}=384 but 366\,ms with 4224, and larger limits use more memory (Table~\ref{tab:support}).

\textbf{Memory.} An uncached NPU compile needs 1.7--3.2\,GB of host RAM and an end-to-end process 1.7--2.4\,GB of RSS, so memory is not a constraint here.

\textbf{Data movement.} With shared DRAM, ``transfer'' is a host-side copy, and payloads are small (per query: 1.5\,KB query vector, 14.6\,KB candidate text, 2.4\,KB prompt). The iGPU reranker's input copy is 3--13\,ms and the NPU's under 0.4\,ms. Reranker tokenization (8--35\,ms, 10--15\% of iGPU S2) is a larger host-side cost; S3 tokenization and detokenization take under 2\,ms. The first inference after loading is up to 2$\times$ slower (NPU S2: 199 versus 84\,ms).

With S3 on the iGPU, a query takes 437\,ms: S1 2\,ms, search 4\,ms, S2 118\,ms, S3 316\,ms (TTFT 81\,ms). Putting S3 on the NPU doubles the latency, and on the CPU it multiplies it by 4. S2 on the NPU does not help sequentially (231\,ms versus 118\,ms) because the NPU reranker is slower than the iGPU's; with overlapped execution, where S2 of the next query runs while S3 decodes, S2 on the NPU reaches 2.45--2.50 queries/s versus 2.38 for all-iGPU, a gain of about 5\%. All-iGPU gains only 7\% from overlap because both stages share one device; S2 on the NPU gains 44\% over its own sequential run, while S3 on the iGPU slows from 316 to about 385\,ms (Sec.~\ref{sec:cont}). Placement also affects output: the NPU reranker reorders candidates (recall@3 0.87 $\rightarrow$ 0.82--0.83), while S2 on the CPU and iGPU rank identically. Real RAG prompts are shorter than the 1k/4k sweep points: top-1/3/8 passages give 213/555/1379 tokens (max 1888), and top-8 takes 764\,ms end to end on the iGPU (TTFT 247\,ms) and 1342\,ms with S3 on the NPU. More passages raise recall (0.74/0.87/0.90) but lower F1 (0.40/0.36/0.25 on the iGPU), so the 1.5B model does worse with longer context; we have not analyzed why.

\subsection{Load}
\begin{figure}[!htb]\centering
\includegraphics[width=0.6\linewidth]{figs/fig_load.pdf}
\caption{Open-loop Poisson arrivals (3 rounds, at least 150 queries per point; error bars: std over rounds). Response time includes queueing.}\label{fig:load}
\end{figure}

Every mapping behaves like a queue with a hard capacity (Fig.~\ref{fig:load}): below it, response time is close to the service time; above it, waiting grows without bound (p50 of 42\,s at 2.0 q/s for S2 and S3 on the NPU). Capacity is 2.4 q/s for S3 on the iGPU and 1.2--1.4 for S3 on the NPU. Between the two S3-on-iGPU mappings the evidence is mixed: in closed-loop runs S2 on the NPU gives 2.45--2.49 q/s versus 2.38 (+4\%), but under Poisson arrivals the two have the same capacity within noise (2.39 vs 2.40, std 0.12--0.14 q/s), the same p50 at 2.0 q/s, and a 12\% lower p95 at 2.5 q/s for the NPU variant. At 1 q/s all-iGPU has the lower median (0.61 versus 0.73\,s). Hence any benefit of an NPU reranker appears only near saturation and is small.

\subsection{Why concurrent devices interfere}\label{sec:cont}
Running S3 decode next to a reranker on another device (Table~\ref{tab:cont}) causes the same slowdown from a thread or a separate process, and none from a tokenize-only thread, so the cause is not the Python GIL but shared memory bandwidth: iGPU TPOT rises 58\% next to an NPU reranker and NPU TPOT 70\% next to an iGPU reranker, while a CPU reranker costs only 8\%. This is why overlapped pipelines gain much less than the sum of their parts.

\section{Limitations}
\begin{itemize}\setlength\itemsep{0pt}
\item \textbf{Two NPU models in one process.} An NPU LLM together with any other NPU model in one process fails at first inference (\texttt{zeMemAllocHost}, null handle), although the same configuration ran on Oct 27. For those mappings the LLM runs in its own process, which adds 0.4--0.6\,ms per call and no measurable end-to-end overhead (842 vs 845\,ms in a control).
\item \textbf{Noise and sample size.} The machine is shared (load average 1--8). Only the main 9 S3-on-iGPU mappings have three rounds; the others have one or two. Quality comparisons use 100 questions with no confidence intervals. The S3 sweep on CPU and NPU covers only 128 output tokens, and its prompts are synthetic.
\item \textbf{Scope.} The corpus is small (25,880 passages), so search is negligible; with a much larger index it would matter. Energy was not measured because power counters need root access, so our comparison is performance only.
\end{itemize}
